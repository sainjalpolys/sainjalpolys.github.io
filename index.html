(03)Architecture

How I architect solutions

Good architecture is a chain of well‑made trade‑offs. I start from the domain and its quality goals, choose the simplest structure that meets them — and write down why.

Patterns I design with

12

  • Layered

    Presentation, domain and data that change independently.

  • Microservices

    Independently deployable services around business capabilities.

  • Event‑driven

    Services react to events instead of calling each other.

  • API gateway

    One secured front door for every client.

  • CQRS

    Writes kept apart from fast, purpose‑built read models.

  • Cache‑aside

    Hot data from cache; the database stays the source of truth.

  • Transactional outbox

    Data and its event saved together, published reliably.

  • Saga

    Long‑running workflows across services, with compensation.

  • Circuit breaker

    Fail fast when a dependency is down; recover gracefully.

  • Sharding

    Data partitioned horizontally to scale reads and writes.

  • Hexagonal

    A domain core kept free of frameworks and I/O.

  • Strangler fig

    Legacy replaced step by step — no big bang.

Design principles

  1. 01

    Domain first

    Boundaries follow the business, not the database.

  2. 02

    API‑first

    Contracts are agreed before the code is written.

  3. 03

    Async by default

    Anything that can wait goes on a queue, so failures don't cascade.

  4. 04

    Secure by design

    Identity, least privilege and managed secrets from the first commit.

  5. 05

    Fast reads

    Search indexes and caches in front of the system of record.

  6. 06

    Ship small, observe all

    CI/CD on every change; logs and metrics from day one.
